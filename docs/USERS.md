# Готовый модуль пользователей

[Оглавление](README.md) · [Модули](MODULES.md)

## Подключение

Сначала `app.UseJwt(settings)`, затем `app.UseUsers("data/accounts.db")`. Первый вызов
задаёт выпуск и проверку токенов, второй добавляет локальные аккаунты и endpoints.
Для cookie-входа дополнительно вызовите `UseCookies()`.

Хранилище создаётся асинхронным этапом `BuildAsync`, до запуска сервера.
Путь — имя файла, не connection string; каталог создаётся автоматически.
SQLite работает в WAL-режиме; SQL параметризован, имена пользователей уникальны
без учёта регистра. Таблицы называются `trexon_users` и `trexon_refresh`.

## Вход через Swagger

`UseUsers()` автоматически добавляет форму логина и пароля в окно **Authorize** на
`/docs`. Сначала создайте аккаунт через `/auth/register` (или используйте существующий),
затем нажмите **Authorize → Войти**. Форма вызывает JSON endpoint login и передаёт
access token стандартной Bearer-схеме Swagger: **Try it out** отправляет его автоматически.
При изменении `UsersOptions.Prefix` или `ApiOptions.DocsPath` адреса формы обновляются сами,
включая размещение приложения под PathBase.

Неверный пароль и ошибки валидации показываются в форме, поле пароля очищается после
запроса. Пароль и refresh token не сохраняются; access token живёт в памяти вкладки.
Перезагрузка страницы сбрасывает вход, автоматического refresh нет. **Logout** в Bearer
удаляет токен из Swagger; уже выданный access JWT сохраняет свой срок действия.
Ручной ввод JWT/API key остаётся доступен. Без `UseUsers()` форма пароля не добавляется;
при `EnableDocs = false` не публикуется и её JavaScript.

Это JWT-вход, он не создаёт cookie-сессию для браузерного WebSocket. Cookie-вход описан ниже.

## HTTP-контракт

| Метод и путь | Запрос | Успешный ответ |
| --- | --- | --- |
| POST `/auth/register` | `username`, `password` | 201 `UserInfo` |
| POST `/auth/login` | `username`, `password` | 200 `TokenPair` |
| POST `/auth/refresh` | `refreshToken` | 200 новая `TokenPair` |
| POST `/auth/logout` | `refreshToken` | 204 |
| GET `/auth/me` | Аутентификация | 200 `UserInfo` |
| GET `/auth/cookie/csrf` | HTTPS | 200 `requestToken`, `headerName` |
| POST `/auth/cookie/login` | LoginRequest + CSRF | 200 `UserInfo`, Set-Cookie |
| POST `/auth/cookie/logout` | CSRF | 204, очистка cookie |

Cookie-endpoints подключаются только при наличии CookieModule. Префикс `/auth`
можно изменить: `UseUsers(path, options => options.Prefix = "/identity")`.
`AllowRegistration = false` запрещает публичную регистрацию с ответом 403.

Username содержит 3–64 ASCII-символа: буквы, цифры, `_`, `.`, `-`.
Пароль содержит 12–128 символов. Хеширование выполняет стандартный PasswordHasher
ASP.NET Core Identity, с 210000 итерациями. Пароли и refresh-токены в открытом виде
в SQLite не сохраняются. Поле `roles` в JSON регистрации игнорируется; начальные роли
задаёт сервер в `RegistrationRoles` (по умолчанию `User`).

Ответ login/refresh:

```json
{
  "accessToken": "...",
  "expiresAt": "2026-10-29T20:15:00+00:00",
  "refreshToken": "...",
  "refreshExpiresAt": "2026-11-05T20:00:00+00:00",
  "user": { "id": "...", "username": "alice", "roles": ["User"] }
}
```

Даты приведены как иллюстрация формата. Клиент берёт реальные значения из ответа.
`UserInfo` никогда не содержит PasswordHash. `StoredUser` — контракт внутреннего
хранилища; не возвращайте его из собственных HTTP-обработчиков.

## Refresh-ротация и выход

Refresh-токен генерируется из 48 криптографически случайных байт; в БД хранится SHA-256.
Каждый login создаёт независимое семейство. Refresh атомарно помечает предыдущий
токен использованным и создаёт новый. Срок жизни семейства не продлевается при ротации;
по умолчанию это 7 дней, настройка допускает до 90 дней.

Повторное предъявление использованного токена отзывает всё семейство, включая последний
выданный refresh. Клиент должен сериализовать refresh-запросы, чтобы два одновременных
обновления не выглядели как повторное использование. Серверная конкурентная проверка
покрыта тестом с двумя соединениями SQLite.

Logout отзывает семейство, но уже выпущенный JWT действует до `expiresAt` с учётом clock skew.
Смена ролей через `IUserStore.SetRolesAsync` тоже отзывает refresh-сессии; активные JWT
и cookie-сессии автоматически не перевыпускаются. Для немедленного отзыва access tokens
понадобится собственная проверка сессии/security stamp на каждом запросе либо внешний провайдер.

## Операции из собственного кода

`IUserAccounts` доступен через DI: `RegisterAsync`, `AuthenticateAsync`, `LoginAsync`,
`RefreshAsync`, `LogoutAsync`; везде передавайте `CancellationToken`.
`AuthenticateAsync` проверяет пароль без выпуска токенов и используется cookie-входом.

Роли назначаются только доверенным серверным кодом. В примере первоначальный admin
создаётся из `TREXON_ADMIN_PASSWORD` до приёма запросов. Существующий аккаунт с таким
именем не повышается в правах без проверки предоставленного пароля.

## Собственное хранилище

Реализуйте `IUserStore`, зарегистрируйте singleton, затем вызовите `app.UseUsers()` без пути.
Интерфейс хранит аккаунты, роли и refresh-семейства; `InitializeAsync` должен быть идемпотентным.
`RotateAsync` обязан атомарно проверить срок/отзыв/использование, погасить старый токен,
добавить новый и отозвать семейство при повторном использовании. Просто SELECT + UPDATE
без транзакции нарушает контракт.

`GetSessionExpiryAsync` возвращает первоначальный срок жизни семейства для нового токена.
Хранилище должно быть безопасно для конкурентного использования. PostgreSQL и другие
сетевые БД подключаются через этот интерфейс; готового PostgreSQL UserStore пока нет.

Microsoft.Data.Sqlite выполняет свои async-вызовы синхронно: это
[ограничение драйвера](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/async).
Библиотека предоставляет отменяемые async-контракты без `Task.Run` и без блокирования
асинхронных задач через `.Result`. Для настоящего неблокирующего сетевого I/O нужен
соответствующий драйвер в реализации `IUserStore`.

## Границы локальных аккаунтов

Это локальный модуль входа для небольшого сервиса, не OAuth/OIDC identity server.
MFA, подтверждение email, восстановление пароля и встроенная блокировка после N
неверных паролей пока отсутствуют. Подключайте rate limiter, а для полного управления
идентификацией используйте внешний провайдер. Просроченные refresh-записи автоматически
не удаляются: фоновых задач нет; очистка и политика хранения — часть эксплуатации хранилища.
